# Assumptions and decisions

Each entry records a decision and the reason for it. **Decided** entries were made by the
project owner. **Assumed** entries were defaults chosen during implementation and still need
confirmation. Add new entries at the end and keep the numbers stable.

## Data model

### D1. The Instagram ID is the primary key of an Instagram account
- **Status:** Decided
- **Decision:** `instagram_accounts.instagram_id` is the primary key, and the only other column is `username`. Every other table references the Instagram ID directly.
- **Reason:** It avoids joins. Workflow runs and tenant links already hold the ID that outbound Instagram calls need.

### D2. Meta user IDs are trusted as given
- **Status:** Decided
- **Decision:** Commenter and DM user IDs from Meta are stored as received, with no users table and no validation.
- **Reason:** Meta is the source of truth for these IDs.

### D3. Tenants and Instagram accounts are many-to-many
- **Status:** Decided
- **Decision:** `tenant_instagram_accounts` links them. Deleting a tenant removes only its links, and deleting an account removes it from every tenant.
- **Reason:** Several tenants may manage one Instagram account without duplicating it.

### D4. An Instagram account may exist with no tenant
- **Status:** Assumed
- **Reason:** It's the simpler rule. Orphaned accounts are not cleaned up automatically.

### D5. IDs are generated by the application
- **Status:** Assumed
- **Decision:** Run and tenant IDs are UUIDs from `crypto.randomUUID()`.
- **Reason:** It works the same on every database driver and needs no database extensions.

## Workflows

### D6. One table per workflow kind
- **Status:** Decided
- **Decision:** There are two tables, `comment_workflow_runs` and `direct_message_workflow_runs`, sharing one set of common columns. A workflow can start another through its context (see D26). Each table has a `workflow` column, because one kind can hold several workflows: `direct_message_workflow_runs` will contain every direct message workflow, starting with `direct_message_after_comment`. Every engine query filters by `workflow`, so workflows sharing a table never touch each other's runs.
- **Reason:** Workflows can be combined, and overlapping runs of one kind (for example, two DM conversations with the same user) are easy to detect.

### D7. `state` is plain indexed text, and `metadata` is JSON
- **Status:** Decided
- **Decision:** `state` holds only the current state name and is indexed. `metadata` (JSONB on Postgres, JSON text on SQLite) holds extra data: the collected email, the origin run, and later things such as messages or tokens spent.
- **Reason:** Workers select runs by state, so it must be a cheap indexed column. Everything else is free-form.

### D8. Comment run lifecycle
- **Status:** Decided
- **Decision:** `comment_received` → send a DM asking for the email → `dm_sent`. After the DM is sent, the handler calls `startDirectMessageAfterComment`. Then the comment is replied to ("Sent you a DM") → `completed`.
- **Reason:** The DM is sent before the comment reply, so the public reply is only posted once the DM is actually out.

### D9. Direct message run lifecycle
- **Status:** Decided
- **Decision:** `awaiting_email` is the only waiting state, and its handler processes replies. The message trigger stores the raw text in `direct_message_workflow_messages` and leaves the run untouched. The worker picks up an `awaiting_email` run only once it has unprocessed messages. The handler then validates them and moves to `email_received` (send a confirmation DM → `completed`), back to `awaiting_email` after a re-prompt DM, or to the final `invalid_email` (see D11). `completed` and `invalid_email` are final states. There is no intermediate "message received" or "invalid" state.
- **Reason:** Triggers only record what happened and never parse. Every decision and every DM happens in a state handler, so it is retried, leased and tested like every other step.

### D10. Dedupe comments and don't message the same person twice
- **Status:** Decided
- **Decision:** Per comment workflow, `(workflow, comment_id)` is unique, so a redelivered webhook is ignored. `(workflow, instagram_account_id, commenter_user_id)` is also unique, so a person a workflow has already messaged from an account is never messaged again by that workflow, even after a later comment. A different comment workflow may still handle the same comment.
- **Reason:** It avoids resending information.

### D11. Replies are validated, and the user is asked again
- **Status:** Assumed
- **Decision:** A reply is accepted when it contains exactly one email-like token and that token is a valid address. Surrounding text is allowed ("sure, it's a@b.co"). Tokens starting with `@` are mentions and are ignored. Otherwise the reply is rejected as one of:
  - `no_email`: no email-like token
  - `invalid_email`: one token, but malformed (`john@gmail`, `a..b@x.com`, ...)
  - `multiple_emails`: more than one distinct token

  Validation happens in the `awaiting_email` handler, never in the trigger. All messages that arrived since the last run of the handler are validated together, and the first valid email wins. If none is valid, they count as one invalid reply, with the reason of the last message. On an invalid reply, the handler DMs a re-prompt that matches the reason, and the run stays in `awaiting_email`. `metadata.invalidReplies` and `metadata.lastInvalidReason` record the attempts. The third invalid reply moves the run to the **final** state `invalid_email`, and nothing more is sent. Messages are marked processed in the same transaction as the handler's result. If the handler fails or loses its lease, they are handled again, and a message that arrives while the handler runs waits for the next round.
- **Reason:** A silent ignore leaves the user without feedback. Capping the re-prompts avoids spamming someone who isn't going to answer.
- **History:** Every message text is kept in `direct_message_workflow_messages` (`received_at`, `processed_at`), including rejected ones.

### D12. A message goes only to the latest listening run
- **Status:** Decided
- **Decision:** When several runs of direct message workflows are waiting on the same account/user pair, an incoming message is stored only for the most recently created run that is in one of its workflow's listening states (for `direct_message_after_comment`, only `awaiting_email`). Older overlapping runs are left untouched, and a newer run that has already finished is skipped.

### D13. Outbound messages are sent at least once
- **Status:** Assumed
- **Decision:** A worker calls Instagram first and then records the transition. If the worker crashes in between, the lease expires and another worker repeats the call.
- **Reason:** Exactly-once delivery would need idempotency keys from Instagram's API.

### D14. Short window for an email that arrives too early
- **Status:** Assumed
- **Decision:** The DM run is created right after the DM call returns. An email that arrives in the milliseconds before that commit finds no waiting run and is ignored.

### D15. Retry and failure policy
- **Status:** Assumed
- **Decision:** A handler that fails keeps its state and is retried after 30 seconds. After 5 attempts the run moves to `failed`, and `metadata.failedState` records which state it failed in. Leases last 60 seconds.

## Infrastructure

### D16. The database is chosen by URL
- **Status:** Decided
- **Decision:** `DATABASE_URL` (`sqlite:` or `postgres://`) selects the driver. Nothing outside `src/db` depends on a particular database.

### D17. The trigger API is simplified
- **Status:** Assumed
- **Decision:** `POST /triggers/comment` and `POST /triggers/message` take a minimal JSON body, not Meta's webhook format. A Meta webhook adapter will translate to these.

### D18. Migrations and queries are plain SQL, with no ORM
- **Status:** Decided
- **Decision:** Each migration is raw SQL written out per dialect in `src/db/migrations.ts`, with no helpers that generate SQL. Queries are hand-written SQL through `Driver.query`. There is no ORM, query builder or migration framework.
- **Reason:** SQL is good enough, and an extra layer would only add complexity.

### D19. Workflows are enabled per Instagram account
- **Status:** Decided
- **Decision:** `instagram_account_workflows (instagram_account_id, workflow)` lists the workflows enabled for each of our Instagram accounts. A row means enabled, and no row means disabled. Workflow names come from code (`receive_dm_comment`, `direct_message_after_comment`), so the column has no `CHECK` constraint and adding a workflow needs no migration.

### D20. What "disabled" means
- **Status:** Assumed
- **Decision:** A trigger for a disabled workflow is rejected with `workflow_disabled`, and no run is created. Workers skip runs of a disabled workflow, so in-flight runs **pause** and resume when the workflow is re-enabled. Runs started by another workflow are still created, but stay paused while their workflow is disabled.
- **Reason:** Disabling should stop all outbound messages at once, without losing conversations already in progress.
- **Consequence:** The comment → email flow needs both `receive_dm_comment` and `direct_message_after_comment` enabled. With only `receive_dm_comment` enabled, users get the DM asking for their email, but their reply is ignored.

### D21. Workflows are built on generic kinds
- **Status:** Decided
- **Decision:** Each workflow kind has a generic module in `src/workflows/kinds/` that owns the kind's table, key columns and trigger. Specific workflows are declared with `defineCommentWorkflow` or `defineDirectMessageWorkflow` and only supply states and handlers. They are registered by kind in `src/workflows/index.ts`, and the triggers in `src/workflows/triggers.ts` dispatch to them.
  - **Comment kind:** a comment starts a run in *every* comment workflow enabled for the account, beginning in that workflow's `initialState`.
  - **Direct message kind:** a message is stored for exactly one run: the latest run, across all *enabled* direct message workflows of the account and user, whose state is one of its workflow's `listeningStates`. Every listening state must have a handler. The kind's `claimFilter` makes the worker pick up a run in a listening state only when it has unprocessed messages, and the handler reads them with `takeMessages(run, ctx)`.
- **Reason:** New workflows, such as more DM flows or other comment flows, reuse storage, dedupe, routing and the trigger contract instead of copying them.

### D22. No separate spawner: the processor migrates on startup
- **Status:** Decided
- **Decision:** There is no spawner CLI. `migrateDatabase` creates the database if needed (for example the SQLite file) and applies pending migrations, and the processor calls it on every start. It is idempotent.
- **Reason:** A separate step added nothing but an extra command to remember.
- **Consequence:** With several processor instances on Postgres, they may race on the first migration. One instance wins, and the others fail on the `schema_migrations` primary key and need a restart. Revisit if that matters (for example, take an advisory lock).

### D23. Shared helpers live in `src/utils`
- **Status:** Decided
- **Decision:** Code that isn't specific to one workflow, such as email parsing and validation (`src/utils/email.ts`) and chunked SQL helpers (`src/utils/sql.ts`), lives in `src/utils`.

### D24. Comments and messages are handled in batches
- **Status:** Decided
- **Decision:** `handleComments` (`onComments`, `POST /triggers/comments {comments: [...]}`) handles a batch of comments in one transaction, so all of its runs are stored or none are. It needs one query to look up the batch's accounts and one for their enabled workflows. Runs are inserted with multi-row `INSERT ... ON CONFLICT DO NOTHING`, in chunks of 500 rows, and `IN (...)` lists are chunked the same way, so parameter counts stay below the SQLite and Postgres limits. `handleComment` is a batch of one, so there is a single code path.
- **Result:** One result per comment, in input order. Within a batch, later entries see earlier ones: a repeated `comment_id` gets `duplicate_comment`, and a second comment by the same commenter gets `commenter_already_engaged`, exactly as if it had come in a later request.
- **HTTP:** A malformed entry rejects the whole request with `400 comments[i]: ...`, and nothing is stored. More than 1000 comments returns `413`.
- **Messages:** `handleMessages` (`onMessages`, `POST /triggers/messages {messages: [...]}`) works the same way. It finds the latest listening run of every conversation in the batch with one chunked query, then stores all routed messages with chunked multi-row inserts, in input order. No run is updated. The result is the same as sending the messages one by one. Results come back in input order, and the HTTP rules are the same as for comments (`400 messages[i]`, `413` above 1000).
- **Reason:** Meta delivers webhook changes in batches, and one round trip per comment would not scale.

### D25. Workflow code layout
- **Status:** Decided
- **Decision:**
  - `src/workflows/core/`: workflow infrastructure, independent of any specific workflow. `engine.ts` holds run storage, leases and transitions, `worker.ts` the worker loop, and `enabled.ts` the per-account enabled workflows.
  - `src/workflows/kinds/`: one generic module per workflow kind (`comment`, `direct_message`).
  - `src/workflows/*.ts`: the specific workflows (`receive-dm-comment.ts`, `direct-message-after-comment.ts`), the registry (`index.ts`) and the triggers (`triggers.ts`).
- **Naming:** A specific workflow is named after what it does within its kind. `receive_dm_comment` is a comment workflow whose commenter receives a DM, and `direct_message_after_comment` is the DM conversation that follows it.

### D26. Handlers change only their own run; other workflows start through the context
- **Status:** Decided
- **Decision:** A state handler returns `{ state, metadata? }`, which affects only the run being handled. To start another workflow, a handler calls that workflow's exported start function with its context, for example `startDirectMessageAfterComment(ctx, { instagramAccountId, dmUserId, origin })`. Start functions are plain functions built on the kind's generic helper (`startDirectMessageWorkflow`), and the started workflow chooses its own initial state.
- **Mechanism:** The context (`WorkflowContext.defer`) queues database writes. The engine runs them in the same transaction that stores the handler's new state. If the handler throws, or the lease was lost, they are dropped. If a deferred write fails, the transaction rolls back, and the run is retried like any failed handler. Outside a handler, `withWorkflowContext(db, fn)` gives the same context and commits its writes in one transaction.
- **Reason:** Starting a workflow is an explicit, named function call, not data in a return value, so workflows don't need to know each other's states or table layout.

### D27. Inbound DMs are stored in their own table
- **Status:** Decided
- **Decision:** `direct_message_workflow_messages (id, run_id, text, received_at, processed_at)` holds every message routed to a direct message run. `id` is auto-increment, so messages keep their arrival order even within one batch. A partial index on unprocessed messages, `(run_id, id) WHERE processed_at IS NULL`, backs the worker's "has new messages" check. Handlers read rows with `ctx.db` and mark them processed with `ctx.defer`. Messages that reach no run are not stored.
- **Reason:** It removes the need for a separate "message received" state and for queueing text in `metadata`, and it keeps a history of what users wrote.

### D28. Each instance chooses which handlers it runs
- **Status:** Decided
- **Decision:** A worker runs the `workflow:state` handlers picked by selectors given at startup: `--handle` (repeatable, comma-separated) or `WORKER_HANDLE`. Selectors are `*`, `workflow`, `workflow:state`, `*:state`, `@group` and `!exclusion`. Named groups (roles) live in one place, `src/workflows/groups.ts`: `@comments`, `@direct-messages`, `@reply-validation`, `@confirmations`. Unknown workflows, states or groups fail at startup. `--no-http` runs a worker-only instance, and `--no-worker` an HTTP-only one.
- **Reason:** Different machines can take different parts of the work (for example, Instagram-facing steps on one, validation on another) without code changes. Leases keep that safe at any number of instances.

### D29. Load tests run real processes
- **Status:** Decided
- **Decision:** `bun run test:load` (`load-tests/`) starts real `processor` processes against one database (SQLite file, and Postgres when `TEST_POSTGRES_URL` is set). One HTTP-only instance takes batched triggers and N worker-only instances process them. The test asserts that every Instagram call happens exactly once across all instances, that every instance did work, and that no run is left leased. A second scenario splits the instances by role. Sizes come from `LOAD_CONVERSATIONS`, `LOAD_WORKERS` and `LOAD_LATENCY_MS`. `bunfig.toml` keeps plain `bun test` on the fast suite in `tests/`.
- **Observed:** 400 conversations (1200 calls) on 4 instances took about 2.4s on SQLite and 2.9s on Postgres. 2000 conversations on 8 instances on SQLite took 6s (about 1000 calls/s).

### D30. Comments are filtered by keyword in the trigger
- **Status:** Decided
- **Decision:** A comment workflow declares which comments start it (`matches`). `receive_dm_comment` starts only for comments containing one of `KEYWORDS` (`["pricing"]`), case-insensitive and whole word or phrase, so "Pricing?" matches and "repricing" does not. The comment trigger now carries the comment `text`. A comment that no enabled workflow matches is ignored with `no_matching_workflow`.
- **Why in the trigger:** This is routing, deciding whether a run starts at all, not processing a reply. If a handler filtered instead, every comment would create a run, and the once-per-commenter rule (D10) would then block that person's later "pricing" comment.

### D31. A customer's automation is "enabled on their account"; the content is in code
- **Status:** Decided
- **Decision:** A customer creates the automation by enabling it on their Instagram account (`instagram_account_workflows`). The keyword, texts and link (`PRICING_LINK`, sent in the final DM) are constants in code. Per-customer configuration can come later as a `config` column, if it is needed.
